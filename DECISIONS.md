# LoopLens design decisions

One line per decision: date, decision, reason.

- 2026-11-06 — Pin LLVM 20 (apt.llvm.org), even though LLVM 23 is current. Reason: brief fixes LLVM 20; the APIs used are stable; avoids chasing release changes before the MVP gate. Revisit after v0.1.
- 2026-11-12 — Install LLVM 20 from Ubuntu 24.04 noble-updates (20.1.2), not apt.llvm.org (20.1.8). Reason: Ubuntu's libllvm20 is already installed system-wide and apt.llvm.org's clang-20 needs a different exact libllvm20 build, so apt refuses to install it. LLVM's API is stable within the 20.x series, so the minor version difference does not matter. CI uses the same packages. Every results file records `opt --version`.
- 2026-11-06 — `looplens-analyze` is a function pass, not a loop pass. Reason: LoopAccessAnalysis and the JSON report want a whole-function view; avoids LoopPassManager canonicalization surprises.
- 2026-11-06 — Iterate loops with `LoopInfo::getLoopsInPreorder()`. Reason: deterministic order (outer before inner, siblings in program order) for FileCheck tests.
- 2026-11-06 — `isRequired() = true`. Reason: the pass is report-only and should also run on clang -O0 (optnone) IR.
- 2026-11-06 — Plugin is built as `LoopLens.so` with no `lib` prefix. Reason: matches `%shlibdir/LoopLens%shlibext` in lit tests.
- 2026-11-12 — `find_package(LLVM REQUIRED CONFIG)` without a version, then check `LLVM_VERSION_MAJOR`. Reason: LLVMConfigVersion.cmake accepts a request only on an exact major.minor match, so `find_package(LLVM 20)` rejects 20.1.x.
- 2026-11-12 — Two repos: a private working repo (planning notes and tooling) and a clean public repo `../looplens-public` produced by `.dev/commit_clean.sh`; only the public repo is pushed. Reason: keep planning notes and tooling out of the portfolio repo without losing their history.
- 2026-11-12 — Work cycle: keep two sub-milestones planned ahead, execute one, review it against its plan, revise the next plan and plan one more; commit after every execute and review. Reason: fast iteration with plans that learn from each execution.
- 2026-11-12 — No dates in the plan; dependency order only. Reason: finish as fast as possible; nothing is deferred because it looks far away.
- 2026-11-12 — Agreement is measured on PolyBench/C for the MVP; TSVC is added in S19 only if it costs at most one session. Reason: the brief lists TSVC under both the agreement objective and Phase 2.
- 2026-11-12 — DECISIONS.md stays in the public repo. Reason: a design log is useful evidence for reviewers and interviewers.
- 2026-11-12 — Test IR is generated once with `clang-20 -O1 -g -fno-discard-value-names -Xclang -disable-llvm-passes … | opt-20 -passes='sroa,loop-simplify,lcssa,loop(loop-rotate)'`, reduced by hand (keeping the debug-info skeleton, `!llvm.loop` and the "Debug Info Version" flag) and checked in; RUN lines run only `looplens-analyze`. Reason: tests see the loop shape LoopVectorize sees and do not change when other LLVM passes change.
- 2026-11-12 — Report line format `  loop header=<hdr> depth=<d> loc=<file>:<line>:<col>` (file name without directory, `loc=<none>` without debug info, unnamed headers as `%N`); location from `Loop::getStartLoc()`. Reason: same location and file field as LoopVectorize remark YAML, so the S17 matcher can join on file:line:col; the column separates two loops on one line.
- 2026-11-12 — `LoopRecord` tracks "has location" with a separate flag, not `Line != 0`. Reason: compiler-generated locations have line 0 and LoopVectorize remark YAML still reports them as `<file>:0:0`; treating them as absent would break the S17 file:line:col join.
- 2026-11-12 — `commit_clean.sh` runs every check (tag, private tests, leak checks, build + tests of the clean copy) before committing in either repo; leak checks include a public top-level allowlist and private-text markers, independent of `.dev/publicignore`; `push_public.sh` reads `.dev/publicignore` instead of its own list. Reason: code review found the two repos could fall out of step, the leak check re-read its own deletion list, and the push guard's list had drifted.
- 2026-11-12 — Trip-count line `    trip kind=<constant|symbolic|unknown> [reason=<r>] count=<n|none> btc=[<scev>] max-btc=[<scev>] symbolic-max-btc=[<scev>]` after each loop line; SCEV text bracketed because it contains spaces. Reason: one greppable line per fact group, values identical to `print<scalar-evolution>` (the oracle) apart from its type prefix.
- 2026-11-12 — Trip count from `getBackedgeTakenCount(L, Exact|ConstantMaximum|SymbolicMaximum)` and `getTripCountFromExitCount`, not `getSmallConstantTripCount` / `getSmallConstantMaxTripCount`. Reason: in LLVM 20 those return 0 above 2^32 and for any 64-bit maximum (e.g. `long n`), measured in session 5.
- 2026-11-12 — Unknown-trip reason is a closed, structural list (not-simplify-form, multiple-exits, exit-cond-not-affine, other), first match wins. Reason: cheap facts from LoopInfo/SCEV without re-implementing SCEV; precise blockers are the classifier's job (S08–S12).
- 2026-11-12 — When a test checks several loops, only the first loop line uses CHECK-NEXT; later loops use CHECK. Reason: each sub-milestone adds per-loop lines, which must not break tests about other facts.
- 2026-11-12 — Supersedes the reason-list entry above: unknown-trip reasons are multiple-exits, needs-scev-predicate (`getPredicatedBackedgeTakenCount` succeeds), exit-cond-not-affine (a leaf compare operand of the exit condition — logical and/or split, integer casts stripped — is neither loop-invariant nor an affine addrec of the loop), exit-cond-not-icmp, other. `not-simplify-form` removed. Reason: code review showed a missing preheader does not stop SCEV (only differing start values do) and that the shape check hid data-dependent exits; LoopVectorize sees loop-simplified IR, so shape is not a trip-count reason.
- 2026-11-12 — Constant trip count computed as BTC + 1 on the APInt, one bit wider (replaces `getTripCountFromExitCount`). Reason: `kind=constant` must always carry a count; the SCEV route could in principle return a non-constant.
- 2026-11-12 — Supersedes the CHECK/CHECK-NEXT entry above: multi-loop tests use CHECK-NEXT throughout and list every per-loop line; a sub-milestone that adds a per-loop line updates those tests. Reason: code review — weakening to CHECK lost adjacency and left inner-loop facts untested; a few lines of churn per sub-milestone is cheaper than weaker tests.
- 2026-11-12 — LoopLens does not canonicalise input loops (no loop-simplify inside the plugin); canonical input is documented in the README. Reason: an analysis pass must not change IR, and in the clang integration (S15) LoopVectorize's own input is already canonical.
- 2026-11-12 — Unknown-trip reason precedence (supersedes the list above): no-exit > needs-scev-predicate (any number of exits) > multiple-exits > exit-cond-not-affine > exit-cond-not-icmp > other; for a single exit, every leaf (through logical and/or, not, freeze; a switch condition counts as an icmp operand) is inspected before deciding. Reason: code review round 3 — infinite loops were called multiple-exits, a countable-with-runtime-check multi-exit loop was called multiple-exits, and the result depended on operand order.
- 2026-11-12 — Loop headers are printed as IR operands with `%` (`%for.body`, `%1`), named ones via `printLLVMNameWithoutPrefix`. Reason: one consistent form, the same as `print<loops>` and as the block names inside SCEV text (`<%for.body>`).
- 2026-11-12 — The ModuleSlotTracker is created lazily (first unnamed header of a function) with `ShouldInitializeAllMetadata=false`. Reason: an eager per-function tracker cost O(#functions × module size) even when every header is named.
- 2026-11-12 — `commit_clean.sh`: build output shown on failure; git identity of the public repo checked before any commit; recovery message if the public step fails after the private commit; tracked-but-deleted files skipped when staging. Reason: code review round 3 (silent failures, possible repo drift, tar abort).
- 2026-11-12 — The private working repo is mirrored to a private GitHub repo for remote work; the public repo is still produced only by the clean-commit step on the laptop. Reason: work can continue away from the laptop without exposing planning notes.
- 2026-11-12 — Induction and form lines after the trip line: `    iv phi=<p> kind=<int|ptr|fp> start=<v> step=<scev> scev=[<scev>] controls-exit=<yes|no>` (one per header phi accepted by `InductionDescriptor::isInductionPHI`, header order; `iv <none>` / `iv <no-preheader>`), then `    form simplify= rotated= lcssa= exiting=<single|multiple> innermost= guarded=`. Reason: one greppable line per fact group; values equal `print<scalar-evolution>` for the phi.
- 2026-11-12 — Use the ScalarEvolution overload of `isInductionPHI` (no SCEV predicates), not the PredicatedScalarEvolution one LoopVectorize uses. Reason: LoopLens reports what is provable without runtime checks; predicate needs are already reported by the trip line (`needs-scev-predicate`).
- 2026-11-12 — Never call `isInductionPHI` on a loop without a preheader; print `iv <no-preheader>`. Reason: in LLVM 20 it dereferences the preheader unchecked and segfaults when the header phi is an add-recurrence (found by `trip-count/no-preheader-same-start.ll` in S04).
- 2026-11-12 — Values printed as IR operands go through one helper (`operandStr`): named locals directly with `%`, everything else via the function's lazy ModuleSlotTracker. Reason: `Value::printAsOperand` without a tracker builds a module-wide slot table per call for constants and unnamed values.
- 2026-11-12 — Memory line `    mem status=<safe|needs-checks|unsafe> checks=<n> max-safe-width=<any|bits|n/a> report=<RemarkName|none>` for innermost loops, `mem <not-innermost>` otherwise; `unsafe` = `!canVectorizeMemory()`, `needs-checks` = `RuntimePointerChecking::Need`; width `n/a` when unsafe. Reason: same tests `print<access-info>` uses; LAA's remark name equals LoopVectorize's remark `Name:`, so S17 can map it directly; the dep checker's width after a refusal is not shown by LLVM and not meaningful.
- 2026-11-12 — Memory and dependence fixtures keep TBAA metadata (`scripts/make_fixture.sh --tbaa`); other fixtures strip it. Reason: LAA uses TBAA (e.g. `a[idx[i]] += 1` is UnsafeDep with TBAA, CantIdentifyArrayBounds without), and clang -O3 always provides it.
- 2026-11-12 — The fixture recipe is a checked-in public script, `scripts/make_fixture.sh`. Reason: reviewers can regenerate every fixture; sessions no longer depend on scratch reducers.
- 2026-11-12 — Dependence lines `    dep kind=<DepName> src=<load|store>:<ptr> dst=<load|store>:<ptr> dist=[<bytes>|none]` after `mem`, in LAA order; `dep <none>` / `dep <not-recorded>`. Distance = address(dst) − address(src) in the same iteration, computed by LoopLens with `getMinusSCEV`, printed only when both pointers are affine add-recurrences of the loop with equal steps. Reason: LLVM 20's `MemoryDepChecker::Dependence` has no distance field; for unequal steps or loaded addresses a single number would be wrong (e.g. `a[idx[i]] += 1` would show 0).
- 2026-11-12 — Access lines `    access <load|store> ptr=<p> kind=<k> stride=<s> [versioned=yes]` for innermost loops, after the dep lines, block then instruction order. Kind from the pointer SCEV, first match: loop-invariant → uniform (0); affine AddRec of the loop with constant step → unit/reverse/constant (step / alloc size; bytes in brackets if not a whole number of elements); loop-invariant non-constant step → symbolic (bytes; `versioned=yes` if in `LAI.getSymbolicStrides()`); contains a load inside the loop → indirect; else unknown. Reason: one rule set readable from `print<scalar-evolution>`; `getPtrStride` also rejects possibly-wrapping pointers, so it is a legality check, not a stride classifier.
- 2026-11-12 — Stride is a cost-model fact, not a legality blocker. Reason: in LLVM 20 strided, symbolic (versioned) and gather accesses are legal; experiments on x86-64 show them vectorized or rejected only as `VectorizationNotBeneficial`.
- 2026-11-12 — Classifier = one rule table (`lib/Classifier.cpp`), evaluated in table order; table order = LoopVectorize's order of checks in LLVM 20 (`canVectorize`: CFG/early exits → phis and instructions → countability → memory (LAA) → SCEV-check budget, then cost model). Primary = first matching rule's category (`rule=` names it), secondary = other matching categories, deduplicated, in table order. Outer loops: `blocker <not-innermost>`. Reason: "primary" then means "what LoopVectorize would stop at first", which is what its remark reports and what S17 scores.
- 2026-11-12 — No blocker for a missing preheader / non-simplified loop, runtime pointer checks, or constant strides. Reason: measured on the fixtures — LoopVectorize runs `simplifyLoop` itself (no-preheader fixture reaches the cost model), versions loops with runtime checks, and vectorizes stride 2 as an interleave group. Stride rule = gathers/scatters and un-versioned symbolic strides only.
- 2026-11-12 — `Classification` is stored in `LoopRecord` and computed by a pure function of the record. Reason: the same result feeds the text report, the JSON report (S13) and remarks (S14) without re-running analyses.
- 2026-11-12 — Recurrence lines `    recur phi=<p> kind=<RecurKind lower case|fixed-order|unsupported> [exact-fp=yes] [ordered=yes]` for every non-IV header phi, after the iv lines; computed only with a preheader (LLVM 20 `AddReductionVar` reads the preheader edge unchecked). Rules `red-exact-fp` and `recur-unsupported` (category reduction) sit after `cfg-multiple-exits`. Reason: same order as `canVectorizeInstrs` (reduction, then fixed-order recurrence, else refuse); x86 does not enable ordered reductions, so any exact-FP reduction is refused (`CantReorderFPOps`).
- 2026-11-12 — Fixtures whose loops contain conditional updates or reductions are captured at LoopVectorize's input (`scripts/make_fixture.sh --o3`: `clang -O3 -mllvm -print-before=loop-vectorize`), keeping TBAA and function attributes. Reason: the canonical-loop recipe skips SimplifyCFG/InstCombine, so `?:` updates stay branches and min/max/any-of reductions and recurrences are not recognised (3 of 7 experiment loops flipped verdict).
- 2026-11-12 — Call lines `    call callee=<@f|indirect> vector=<intrinsic|vfabi|tli|no> mem=<none|read|write> [math-lib=yes]` and `    nonsimple <load|store>:<ptr> why=<volatile|atomic>` for innermost loops, after the access lines; debug and assume-like intrinsics skipped. The `vector=` test reproduces `LoopVectorizationLegality::canVectorizeInstrs` (LLVM 20, lines 895-930), with its static `isTLIScalarize` approximated by `TLI.isFunctionVectorizable`. Rules `call-no-vector-form` and `mem-non-simple` (category call-or-unsafe-memop) follow the reduction rules. Reason: same acceptance test as LoopVectorize; `math-lib=yes` carries LLVM's own "-fno-math-errno" hint for S12's fix text.
- 2026-11-12 — CFG line `    cfg blocks= predicated= switches= exits= early-exit=<none|countable|uncountable>` after `form` for innermost loops; predication via `LoopAccessInfo::blockNeedsPredication`, early-exit countability via per-block `getExitCount`. Rules `cfg-uncountable-early-exit` (first), `cfg-multiple-exits`, `cfg-unpredicable` (call without vector form or non-simple access in a predicated block) head the table. Reason: LLVM 20 checks the CFG and if-conversion before instructions (so `NoCFGForSelect` precedes `CantVectorizeLibcall`), vectorizes switches/nested ifs/conditional stores, and refuses uncountable early exits by default.
- 2026-11-12 — Evidence and fix: one template pair per rule (not per category), printed as `    evidence …` / `    fix …` after `blocker` when a rule fired; values quoted from the record (first matching fact). Fix text is worded for LLVM 20; only fixes verified against LLVM (pragma vectorize(enable) for a strict FP sum, -fno-math-errno for sinf) are claimed as working in the README. Reason: rules are the precise reasons; unverified advice must not read as a promise.
- 2026-11-12 — Rule `cfg-multiple-exits` removed. Reason: a hand-written loop with two countable exits reaches LLVM 20's cost model (`control-flow/countable-multi-exit.ll`), so several exiting blocks are not a legality blocker; uncountable early exits stay a rule.
- 2026-11-12 — JSON report as JSON Lines (one object per loop) written with `llvm::json::OStream` to `-looplens-json=<path>`, a process-wide stream opened (truncated) on first use. Reason: the pass runs per function and S16 runs one clang per file; lines need no module-level state and concatenate. Trip counts are strings (may exceed 64 bits).
- 2026-11-12 — With clang the plugin must also be loaded via `-Xclang -load -Xclang LoopLens.so` for `-mllvm -looplens-*` options. Reason: `-fpass-plugin=` loads the plugin after LLVM option parsing ("Unknown command line argument"); verified with a scratch plugin.
- 2026-11-12 — Remarks: one `OptimizationRemarkAnalysis` per innermost loop, pass `looplens`, name = primary rule id or `Vectorizable`, location `Loop::getStartLoc()`, code region = header, args `Category`/`Rule`/`Secondary`/`Evidence`/`Fix` (Evidence/Fix omitted when vectorizable). Reason: same location as LoopVectorize's per-loop `MissedDetails`/`Vectorized` remarks (verified in one opt run), so S17 joins on DebugLoc; emitting for vectorizable loops too lets S17 distinguish "says vectorizable" from "not seen". Note for S17: LV's specific reasons (e.g. `UnsafeDep`) are located at the offending instruction, not the loop start.
- 2026-11-12 — Under clang, LoopLens runs at the VectorizerStart extension point (skipped at `OptimizationLevel::O0`); option `-looplens-text` (default true) turns the stderr report off. Reason: between that point and LoopVectorize LLVM 20 only runs LoopRotate, LoopDeletion, opt-in LoopDistribute and InjectTLIMappings; LLVM 20's -O0 pipeline also invokes the extension point, where LoopLens reported unoptimised code (test `clang/o0.c`).
- 2026-11-12 — Loop hints `llvm.loop.vectorize.enable` / `llvm.loop.vectorize.width` are read (`hints` line, only when present); a forced vectorize or width > 1 disables `red-exact-fp`. Reason: `LoopVectorizeHints::allowReordering()` lets LoopVectorize reorder FP reductions then (verified: pragma'd float sum vectorizes). Other hints (`assume_safety`, `disable`) are not modelled yet — S18 candidates.
- 2026-11-12 — Correction to the report-line entry: `loc=` prints the DILocation's file name as recorded by clang (bare for the hand-made fixtures, the given path such as `test/clang/json.c` under clang), not a basename. Reason: it must equal the `File:` of LLVM's remark YAML for the S17 join; both come from the same DIFile.
- 2026-11-12 — PolyBench/C 4.2.1-beta is fetched by `scripts/fetch_polybench.sh` (pinned URL and SHA-256 `426519ee…89a4`) and compiled as shipped (no `POLYBENCH_USE_RESTRICT`, generic x86-64, `-O3 -g`) by `scripts/collect.sh`, which only passes the downloaded sources to clang as paths. Raw outputs stay in `results/raw/` (ignored); `results/collect_summary.csv` and its toolchain file are committed. Reason: explain what LLVM does with the benchmark as published; reproducible from a checksum-verified download.
- 2026-11-12 — Agreement metric (`scripts/agreement.py`, `docs/methodology.md`): LoopVectorize's reason remarks are attributed to the next per-loop remark of the same file; its first reason, mapped by a glob table to a LoopLens category (`cost` ↔ `stride`), is compared with LoopLens's primary; loops match on file, line, column and function. Unmapped names, one-sided and ambiguous loops are reported, never guessed. Reason: LoopVectorize emits reasons before the per-loop remark and at instruction locations; inlined kernels duplicate source locations across functions (PolyBench doitgen).
- 2026-11-12 — README result numbers are generated by `scripts/results_table.py` from `results/*.csv` between marker comments. Reason: the "never invent numbers" rule — no figure is typed by hand.
- 2026-11-12 — `red-exact-fp` moved after the memory rules. Reason: LoopVectorize checks exact-FP reordering in `processLoop` after legality (LoopVectorize.cpp:10485), so `UnsafeDep` is its first reason when both apply (4 PolyBench loops).
- 2026-11-12 — At the clang extension point LoopLens runs LoopSimplify + LCSSA before itself (`-looplens-canonicalize`, default on). Reason: LoopVectorizePass canonicalises loops itself before its checks; without this LoopLens missed reductions in loops that had no preheader yet (4 PolyBench loops). `scripts/codegen_unchanged.sh` verifies identical assembly with and without the plugin for all 30 kernels.
- 2026-11-12 — TSVC_2 (UoB-HPC, commit 911fc639, SHA-256 per file) is the held-out check: fetched by `scripts/fetch_tsvc.sh`, compiled by `scripts/collect.sh --list`, scored with `agreement.py --prefix tsvc_`; never committed (no licence published; owner decision U8 on keeping the results public). No LoopLens change is made because of TSVC. Reason: PolyBench was used to fix rules (S18), so an untouched second suite is needed for an honest number.
- 2026-11-12 — Scorer: `VectorizationNotBeneficial`, `UncountableEarlyExitLoopsDisabled`, `UncountableEarlyExitUnsupported`, `StructCallVectorizationUnsupported` are per-loop verdicts (they close their loop; no `MissedDetails` follows). Reason: LoopVectorizePass::processLoop emits them after legality and returns; found on TSVC (first scorer run kept as `results/tsvc_agreement_summary_before.csv`).
- 2026-11-12 — v0.1 release shape: README leads with the problem and a worked example that is itself a lit test (`test/clang/readme-example.c`); results come only from `scripts/results_table.py --update-readme`; `scripts/reproduce.sh` regenerates every committed number; CHANGELOG.md is public (added to `PUBLIC_TOPLEVEL`). The tag is made on the laptop (U10). Reason: nothing a reader sees can drift from what the code does or the data says.
- 2026-11-13 — Phase 2 re-targeted (option A, owner-approved via the issues list): `looplens-repair` versions loops on "the accumulated loop-invariant address does not overlap any address read" and promotes that address to a register in the fast copy, turning LoopVectorize's `UnsafeDep` into a reduction. Reason: LLVM 20 already versions loops that only need runtime alias checks (0 such blocked loops in PolyBench/TSVC), while 7 PolyBench loops are blocked by this pattern; LLVM's LoopVersioningLICM refuses them.
- 2026-11-13 — `looplens-repair` is a separate function pass (opt name `looplens-repair`; clang `-mllvm -looplens-repair`, off by default) that returns `PreservedAnalyses::none()` when it changes IR; correctness is checked in strict FP (byte-identical PolyBench outputs, `scripts/differential.sh`), because with `-ffast-math` the newly vectorized reductions legitimately reassociate. Reason: separates "the transform is correct" from "the programmer allowed FP reordering".
- 2026-11-13 — `red-exact-fp` asks the target: it does not fire for an ordered reduction when `TTI::enableOrderedReductions()` is true (AArch64). Reason: LoopVectorize 20 uses that TTI hook (LoopVectorize.cpp:10476-10483); the rule was x86-only before (tests `reduction/fp-sum-strict-aarch64.ll`, `clang/fp-sum-aarch64.c`).
- 2026-11-13 — Agreement is measured on three targets: generic x86-64, `-march=x86-64-v4` (AVX-512) and AArch64 (compile-only; headers from Ubuntu's cross libc unpacked with `apt-get download` + `dpkg -x`, `scripts/fetch_aarch64_sysroot.sh`). `collect.sh --cflags`, prefixed results files. Reason: cost and legality decisions are target-specific (issue 4); the generic-x86 numbers alone overstated generality.
- 2026-11-13 — `stride-gather` fires for an indirect access only when the target has no legal masked gather/scatter for its element type (`TTI::isLegalMaskedGather/Scatter`, asked for a 256-bit vector); access lines gain `gather=legal`. Reason: with AVX-512 LoopVectorize vectorizes gathers (7 TSVC loops), on generic x86-64 it rejects them.
- 2026-11-13 — Scorer: `Interleaved` (a `!Passed` remark: VF 1 chosen, loop only interleaved) is a per-loop verdict with category `cost`. Reason: found on AArch64, where it otherwise leaked into the next loop's reasons.
- 2026-11-13 — Rule `cost-strided` (category stride, after `stride-gather`): every access of the loop has a constant stride beyond 8 elements (LoopVectorize's interleave-group factor) and no legal gather. Derived from TSVC's cost-model misses, so TSVC is no longer held out for it. A general TTI cost estimate (vector vs scalar body cost) was tried and rejected: it raised AArch64 PolyBench from 112 to 166 of 188 but dropped x86 PolyBench from 163 to 132.
- 2026-11-13 — Loop hints: new category `hint` with rule `hint-vectorize-disabled` (first in the table; `vectorize(disable)` arrives as `vectorize_width(1)`), and forced vectorization (`vectorize(enable)`, `assume_safety`, width > 1) disables the cost rules (`stride-gather`, `cost-strided`). Reason: LoopVectorize reads hints first and skips its profitability check for forced loops (`clang/hints.c`); `assume_safety` needs no LoopLens rule because LoopAccessAnalysis already honours `llvm.loop.parallel_accesses`.
- 2026-11-13 — Scorer: a `VectorizationNotBeneficial` verdict followed by `Interleaved` at the same location in the same function is one loop (LoopVectorize decided against vectors, then interleaved the scalar loop). Reason: on AArch64 each such loop was counted twice (188 "matched" loops for 163 innermost loops); found when same-key pairing (issue 7) turned the duplicates into `ambiguous`.
- 2026-11-13 — Every rule's fix text is checked by `scripts/verify_fixes.sh` on a before/after example (`bench/fixes/`, public), result in `results/fix_verification.csv`; the README claims only what that file says. Fix text for `mem-unsafe-dep` changed to "make the dependence distance at least the vector length". Reason: issue 8 — two of thirteen fixes did not hold as first written.
- 2026-11-13 — Rule `mem-call-writes` (call-or-unsafe-memop, after `mem-non-simple`): a call with a vector variant (`vector=tli`/`vfabi`) that may write memory. Reason: with `-fveclib=libmvec`, errno-setting `sinf` has a vector variant but LoopAccessAnalysis still refuses it (`CantVectorizeInstruction`); found by the issue-9 coverage test.
- 2026-11-13 — Classification tests (`test/classify/`) use IR captured at LoopVectorize's input (`make_fixture.sh --o3`); fact tests keep the canonical recipe. Reason: a classification is only meaningful against what LoopVectorize really sees (issue 10); fact tests deliberately include shapes LV never sees.
- 2026-11-13 — Second metric "all-reasons coverage": all categories among LoopVectorize's reasons are in LoopLens's primary ∪ secondary. Reason: issue 11 — the primary-only metric ignored LV's later reasons; reported next to, not instead of, the headline.
- 2026-11-13 — `%p` in `-looplens-json` is replaced by the process ID. Reason: issue 13 — one shared path written by parallel processes would interleave or truncate; LLVM's profile files use the same convention.
- 2026-11-14 — final-stretch order and scope (PLAN_FINAL_STRETCH.md) — owner-approved. Order S22 → S24 → S23 → S25, then optional X1, then S26–S28 without waiting for the v0.2 tag; S22 also explains the loops the repair does not fix; S24 adds overlap tests and a fast-math tolerance; S23 compares only equal flag sets and its real run is an owner step.
- 2026-11-14 — `looplens-repair` versions a loop only if it needs at most `-looplens-repair-max-checks` (default 8) runtime address-range checks. Reason: same budget as LLVM's `-runtime-memory-check-threshold`; an unbounded check could cost more than the loop (S22 threshold tests).
- 2026-11-14 — Repair correctness evidence (S24): strict-FP byte equality on PolyBench SMALL and MEDIUM; overlap driver built at -O0 / -O3 / -O3+repair with `-ffp-contract=off` and exact `%a` output, plus a mutation test that forces the fast path; fast-math compared against a tolerance fixed in advance (relative ≤ 1e-6, or absolute ≤ 0.011 below 1e4: one unit of PolyBench's `%0.2lf`). Reason: PolyBench arrays never overlap, so only a dedicated driver runs the fallback copy; a tolerance chosen after seeing the data would prove nothing.
