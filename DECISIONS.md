# LoopLens design decisions

One line per decision: date, decision, reason.

- 2026-11-06 — Pin LLVM 20 (apt.llvm.org), even though LLVM 23 is current. Reason: brief fixes LLVM 20; the APIs used are stable; avoids chasing release changes before the MVP gate. Revisit after v0.1.
- 2026-11-12 — Install LLVM 20 from Ubuntu 24.04 noble-updates (20.1.2), not apt.llvm.org (20.1.8). Reason: Ubuntu's libllvm20 is already installed system-wide and apt.llvm.org's clang-20 needs a different exact libllvm20 build, so apt refuses to install it. LLVM's API is stable within the 20.x series, so the minor version difference does not matter. CI uses the same packages. Every results file records `opt --version`.
- 2026-11-06 — `looplens-analyze` is a function pass, not a loop pass. Reason: LoopAccessAnalysis and the JSON report want a whole-function view; avoids LoopPassManager canonicalization surprises.
- 2026-11-06 — Iterate loops with `LoopInfo::getLoopsInPreorder()`. Reason: deterministic order (outer before inner, siblings in program order) for FileCheck tests.
- 2026-11-06 — `isRequired() = true`. Reason: the pass is report-only and should also run on clang -O0 (optnone) IR.
- 2026-11-06 — Plugin is built as `LoopLens.so` with no `lib` prefix. Reason: matches `%shlibdir/LoopLens%shlibext` in lit tests.
- 2026-11-12 — `find_package(LLVM REQUIRED CONFIG)` without a version, then check `LLVM_VERSION_MAJOR`. Reason: LLVMConfigVersion.cmake accepts a request only on an exact major.minor match, so `find_package(LLVM 20)` rejects 20.1.x.
- 2026-11-12 — Two repos: a private working repo (planning notes and tooling) and a clean public repo `../looplens-public` produced by `.dev/commit_clean.sh`; only the public repo is pushed. Reason: keep planning notes and tooling out of the portfolio repo without losing their history.
- 2026-11-12 — Work cycle: keep two sub-milestones planned ahead, execute one, review it against its plan, revise the next plan and plan one more; commit after every execute and review. Reason: fast iteration with plans that learn from each execution.
- 2026-11-12 — No dates in the plan; dependency order only. Reason: finish as fast as possible; nothing is deferred because it looks far away.
- 2026-11-12 — Agreement is measured on PolyBench/C for the MVP; TSVC is added in S19 only if it costs at most one session. Reason: the brief lists TSVC under both the agreement objective and Phase 2.
- 2026-11-12 — DECISIONS.md stays in the public repo. Reason: a design log is useful evidence for reviewers and interviewers.
- 2026-11-12 — Test IR is generated once with `clang-20 -O1 -g -fno-discard-value-names -Xclang -disable-llvm-passes … | opt-20 -passes='sroa,loop-simplify,lcssa,loop(loop-rotate)'`, reduced by hand (keeping the debug-info skeleton, `!llvm.loop` and the "Debug Info Version" flag) and checked in; RUN lines run only `looplens-analyze`. Reason: tests see the loop shape LoopVectorize sees and do not change when other LLVM passes change.
- 2026-11-12 — Report line format `  loop header=<hdr> depth=<d> loc=<file>:<line>:<col>` (file name without directory, `loc=<none>` without debug info, unnamed headers as `%N`); location from `Loop::getStartLoc()`. Reason: same location and file field as LoopVectorize remark YAML, so the S17 matcher can join on file:line:col; the column separates two loops on one line.
- 2026-11-12 — `LoopRecord` tracks "has location" with a separate flag, not `Line != 0`. Reason: compiler-generated locations have line 0 and LoopVectorize remark YAML still reports them as `<file>:0:0`; treating them as absent would break the S17 file:line:col join.
- 2026-11-12 — `commit_clean.sh` runs every check (tag, private tests, leak checks, build + tests of the clean copy) before committing in either repo; leak checks include a public top-level allowlist and private-text markers, independent of `.dev/publicignore`; `push_public.sh` reads `.dev/publicignore` instead of its own list. Reason: code review found the two repos could fall out of step, the leak check re-read its own deletion list, and the push guard's list had drifted.
- 2026-11-12 — Trip-count line `    trip kind=<constant|symbolic|unknown> [reason=<r>] count=<n|none> btc=[<scev>] max-btc=[<scev>] symbolic-max-btc=[<scev>]` after each loop line; SCEV text bracketed because it contains spaces. Reason: one greppable line per fact group, values identical to `print<scalar-evolution>` (the oracle) apart from its type prefix.
- 2026-11-12 — Trip count from `getBackedgeTakenCount(L, Exact|ConstantMaximum|SymbolicMaximum)` and `getTripCountFromExitCount`, not `getSmallConstantTripCount` / `getSmallConstantMaxTripCount`. Reason: in LLVM 20 those return 0 above 2^32 and for any 64-bit maximum (e.g. `long n`), measured in session 5.
- 2026-11-12 — Unknown-trip reason is a closed, structural list (not-simplify-form, multiple-exits, exit-cond-not-affine, other), first match wins. Reason: cheap facts from LoopInfo/SCEV without re-implementing SCEV; precise blockers are the classifier's job (S08–S12).
- 2026-11-12 — When a test checks several loops, only the first loop line uses CHECK-NEXT; later loops use CHECK. Reason: each sub-milestone adds per-loop lines, which must not break tests about other facts.
- 2026-11-12 — Supersedes the reason-list entry above: unknown-trip reasons are multiple-exits, needs-scev-predicate (`getPredicatedBackedgeTakenCount` succeeds), exit-cond-not-affine (a leaf compare operand of the exit condition — logical and/or split, integer casts stripped — is neither loop-invariant nor an affine addrec of the loop), exit-cond-not-icmp, other. `not-simplify-form` removed. Reason: code review showed a missing preheader does not stop SCEV (only differing start values do) and that the shape check hid data-dependent exits; LoopVectorize sees loop-simplified IR, so shape is not a trip-count reason.
- 2026-11-12 — Constant trip count computed as BTC + 1 on the APInt, one bit wider (replaces `getTripCountFromExitCount`). Reason: `kind=constant` must always carry a count; the SCEV route could in principle return a non-constant.
- 2026-11-12 — Supersedes the CHECK/CHECK-NEXT entry above: multi-loop tests use CHECK-NEXT throughout and list every per-loop line; a sub-milestone that adds a per-loop line updates those tests. Reason: code review — weakening to CHECK lost adjacency and left inner-loop facts untested; a few lines of churn per sub-milestone is cheaper than weaker tests.
- 2026-11-12 — LoopLens does not canonicalise input loops (no loop-simplify inside the plugin); canonical input is documented in the README. Reason: an analysis pass must not change IR, and in the clang integration (S15) LoopVectorize's own input is already canonical.
- 2026-11-12 — Unknown-trip reason precedence (supersedes the list above): no-exit > needs-scev-predicate (any number of exits) > multiple-exits > exit-cond-not-affine > exit-cond-not-icmp > other; for a single exit, every leaf (through logical and/or, not, freeze; a switch condition counts as an icmp operand) is inspected before deciding. Reason: code review round 3 — infinite loops were called multiple-exits, a countable-with-runtime-check multi-exit loop was called multiple-exits, and the result depended on operand order.
- 2026-11-12 — Loop headers are printed as IR operands with `%` (`%for.body`, `%1`), named ones via `printLLVMNameWithoutPrefix`. Reason: one consistent form, the same as `print<loops>` and as the block names inside SCEV text (`<%for.body>`).
- 2026-11-12 — The ModuleSlotTracker is created lazily (first unnamed header of a function) with `ShouldInitializeAllMetadata=false`. Reason: an eager per-function tracker cost O(#functions × module size) even when every header is named.
- 2026-11-12 — `commit_clean.sh`: build output shown on failure; git identity of the public repo checked before any commit; recovery message if the public step fails after the private commit; tracked-but-deleted files skipped when staging. Reason: code review round 3 (silent failures, possible repo drift, tar abort).
- 2026-11-12 — The private working repo is mirrored to a private GitHub repo for remote work; the public repo is still produced only by the clean-commit step on the laptop. Reason: work can continue away from the laptop without exposing planning notes.
